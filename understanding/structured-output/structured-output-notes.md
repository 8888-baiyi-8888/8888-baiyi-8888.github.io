## 一、目的

结构化输出的目标只有一个：**让下游程序可以直接使用大模型结果。**

它不是为了“看起来像 JSON”，而是为了让结果真正具备工程可用性，也就是：

- 能直接解析
- 能校验
- 能进入自动化流程
- 出错时能统一处理

如果输出结果只能让人看懂，却不能被程序稳定接住，那么它就还不算真正意义上的结构化输出。

## 二、核心结论

### 1. 处理优先级

面对不同模型厂商时，推荐按下面顺序处理：

1. 优先查看模型官网是否提供结构化输出说明
2. 如果官网支持原生 schema 输出，优先采用官方方式
3. 如果官网只支持 JSON 输出，就补上下游校验
4. 如果官网没有明确说明，或者实测不稳定，就退回到提示词约束 + 程序校验 + 重试机制

这里最重要的不是“统一写一套万能提示词”，而是先判断模型本身有没有稳定的原生约束能力。

### 2. 结构化输出的本质

结构化输出不是单纯的提示词问题，而是一个完整的工程问题。它至少包含四层：

- 模型能力
- 输出约束
- 下游校验
- 异常处理

也就是说，结构化输出是否稳定，从来不只取决于“提示词写得好不好”，而取决于整个链路有没有被设计完整。

## 三、为什么不能只靠提示词

不能只靠提示词，原因并不复杂。

不同模型在这些方面存在明显差异：

- 对提示词模板的敏感度不同
- 对同义表达的理解不同
- 对 JSON、schema、字段约束的执行能力不同

因此，不能假设：

**在 OpenAI 上能稳定输出的提示词，在阿里、Qwen 或其他模型上也一定稳定。**

提示词当然仍然重要，但它更像是“辅助约束”，而不是唯一的可靠约束。真正面向生产时，必须把“提示词有效”与“程序可依赖”分开看。

## 四、推荐开发原则

### 1. 以官网说明为准

如果模型官网已经给出结构化输出文档，优先按照官网要求的参数与格式实现。不要先套一层自己的抽象，再反过来猜官方能力边界。

### 2. 优先使用原生结构化能力

推荐顺序如下：

1. 官方 JSON Schema / Structured Outputs
2. 官方 JSON Object / JSON Mode
3. 提示词约束 + 下游校验

越靠前，约束能力通常越强；越靠后，越依赖模型“自觉”遵守格式。

### 3. 必须做下游校验

即使模型支持结构化输出，也不能完全相信返回值。至少要做三层检查：

1. 是否能解析为 JSON
2. 是否符合 schema
3. 是否符合业务规则

结构化输出的目标是给程序使用，而程序使用就意味着必须有明确的验收标准。

### 4. 失败必须可恢复

结构化输出一定会失败，所以系统必须具备恢复能力，至少包括：

- 重试
- 降级
- 兜底
- 日志记录

如果失败后只能人工排查，那它就还不够适合自动化流程。

## 五、推荐架构

一个更稳妥的结构化输出流程，可以理解为下面这条主链路：

```text
输入任务
  ↓
构造 Prompt / Messages
  ↓
选择模型结构化模式
  ├─ JSON Schema
  ├─ JSON Object
  └─ Prompt-only
  ↓
模型调用
  ↓
结果解析
  ├─ JSON 校验
  ├─ Schema 校验
  └─ 业务校验
  ↓
结果分流
  ├─ 成功 → 下游使用
  ├─ 可修复失败 → 重试
  └─ 不可修复失败 → 降级 / 人工处理
```

这个架构的重点在于：把“生成”与“验收”彻底分开。模型负责给结果，程序负责决定这个结果能不能进入下游。

## 六、开发规范

### 1. schema 优先

先定义业务结果结构，再写提示词。不要先让模型随便输出，再回头猜它到底想表达什么字段。

### 2. 字段要清晰

字段名应稳定、明确，避免缩写和歧义。例如：

```json
{
  "title": "文档标题",
  "summary": "摘要",
  "keywords": ["关键词1", "关键词2"],
  "confidence": 0.95
}
```

字段名一旦进入下游流程，就不再只是“展示文本”，而是接口契约的一部分。

### 3. 结构不要太深

层级越深，越容易出错。一般建议控制在 2 到 4 层以内，避免把简单任务设计成复杂嵌套对象。

### 4. 必填字段不要过多

必填字段过多会降低稳定性。只把真正关键的字段放进 `required`，其余字段宁可设为可选，也不要把生成稳定性压得过低。

## 七、失败处理建议

结构化输出的常见失败包括：

- 不是合法 JSON
- JSON 合法但字段不对
- 字段类型错误
- 缺字段
- 值虽然合法但不符合业务要求

推荐按下面的顺序处理：

```text
模型返回
  ↓
JSON 解析失败？ → 重试
  ↓
Schema 校验失败？ → 重试 / 降级
  ↓
业务校验失败？ → 重试 / 低置信标记
  ↓
成功进入下游
```

这里的关键点是：不要把所有失败都视为同一种失败。解析失败、schema 失败、业务失败，本质上属于不同层级，应该有不同的处理策略。

## 八、多模型场景建议

如果系统同时接多个模型，不要让业务代码直接适配每个厂商的差异。更合理的做法是增加统一封装层，例如：

- OpenAI 适配器
- Qwen 适配器
- Schema 校验器
- 重试策略
- 降级策略

这样业务层只关心统一结果，不需要关心底层到底是哪个厂商、哪个参数名、哪种约束格式。

换句话说，多模型系统的关键不是“让业务代码懂所有厂商”，而是“让适配层替业务代码吸收厂商差异”。

## 九、最终结论

一句话总结：

**复杂自动化流程里，结构化输出应优先遵循模型官网；官网支持原生结构化就优先用原生能力；否则就使用提示词约束 + 下游校验 + 重试降级。**

如果再压缩成更工程化的一句表达，那就是：

**结构化输出的目标，不是让模型输出得像结构化，而是让系统真的能够稳定消费它。**
