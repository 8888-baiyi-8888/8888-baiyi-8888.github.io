## 概要

这篇文章最重要的观点是：很多 Agent 的性能瓶颈，不一定先来自模型本身，而是来自围绕模型构建的执行外壳，也就是 `harness`。LangChain 在不更换模型、只调整 harness 的情况下，把他们的编码 Agent 在 `Terminal Bench 2.0` 上的分数从 `52.8` 提升到了 `66.5`，从榜单 Top 30 外推进到 Top 5。

这里的 `Harness Engineering`，本质上是在做模型之外的系统设计。它关心的不是“模型是否更聪明”，而是“如何通过 prompt、工具、middleware、执行流程和反馈回路，把模型的能力更稳定地导向目标任务”。

## 什么是 Harness Engineering

如果把模型理解成一个有潜力但不稳定的执行者，那么 harness 就是包在模型外面的运行系统。它负责约束模型、向模型提供环境信息、组织工具调用，并在关键节点插入额外的控制逻辑。

文章里的定义可以概括成：

- harness 的目标，是把模型本身起伏很大的智能，塑造成更适合具体任务的执行能力
- harness engineering 的重点，是围绕模型建立一层系统，使其在任务表现、token 效率、延迟和稳定性上更可控

LangChain 在实验里刻意收缩优化空间，只重点改三类旋钮：

- `System Prompt`
- `Tools`
- `Middleware`

这也说明一件事：很多时候，不需要一开始就重训模型，先把围绕模型的这层系统打磨好，就已经能带来明显提升。

## 文章里最核心的几类改进

### 1. 用 Trace（执行轨迹）做外循环改进

文章里很关键的一点，是把 `trace analysis`（执行轨迹分析）变成了可重复运行的能力，而不是靠人工零散看日志。

他们的流程大致是：

1. 从 LangSmith 拉取实验 trace（执行轨迹）
2. 并行启动错误分析 Agent，分别分析失败模式
3. 由主 Agent 汇总问题和修改建议
4. 再基于这些反馈，对 harness 做定向改动

这和 boosting 有点像，重点盯住上一轮最容易失败的地方继续修。它的工程意义很强：Agent 的改进不再靠感觉，而是靠 trace（执行轨迹）驱动的闭环迭代。

### 2. 强化“构建 - 验证 - 修复”的闭环

文章指出，当前模型虽然有自我改进潜力，但默认并不会自然进入严格的验证循环。最常见的失败模式是：Agent 写完方案，重新看一眼自己的代码，觉得差不多了，然后就停了。

LangChain 因此在 system prompt 里明确加入了四步工作流：

1. `Planning & Discovery`
2. `Build`
3. `Verify`
4. `Fix`

这里最关键的是 `Verify`。他们特别强调，Agent 必须：

- 主动运行测试
- 读取完整输出
- 对照任务规范，而不是只对照自己写的代码

此外，他们还加入了 `PreCompletionChecklistMiddleware`。它会在 Agent 准备退出前拦截一次，提醒它执行完整验证。这种做法非常像“退出前强制再检查一次”，目的就是避免 Agent 过早结束任务。

### 3. 主动给 Agent 注入环境上下文

文章认为，Harness Engineering 其实也是 Context Engineering 的一个重要落点，因为很多错误来自 Agent 对环境理解不充分。

他们主要做了几件事：

- 启动时用 `LocalContextMiddleware` 探测当前目录、父子目录结构
- 通过 shell 命令寻找 Python 等本地工具
- 在 prompt 中明确说明代码会被程序化测试验证
- 注入时间预算提醒，推动 Agent 在超时前完成验证

这部分的核心思想是：不要让 Agent 靠自己慢慢猜环境。环境信息、约束信息、评测标准这些本来就可以确定的内容，应当由 harness 提前整理好再交给 Agent。

### 4. 检测并打断坏循环

文章里提到一个很典型的问题：Agent 一旦选错方案，往往会在同一路径上不断做小修小补，形成所谓的 `doom loop`。

LangChain 的做法是加入 `LoopDetectionMiddleware`，通过追踪同一文件被反复编辑的次数，在超过阈值后给出额外提醒，要求 Agent 重新考虑当前方案。

这个机制不是从根上解决模型推理问题，而是用工程上的 guardrail 去限制一种已知坏模式。文章也明确承认，这类设计很大程度上是在适配“今天的模型还不够稳定”这一现实。

### 5. 推理预算要按阶段分配

他们还讨论了 reasoning budget 的分配问题。文章里的经验不是“全程最高推理强度最好”，而是要根据阶段来花算力。

他们发现：

- 高推理预算对前期规划有帮助
- 后期验证阶段同样需要更多推理来发现错误
- 全程都用最高档，反而可能因为时间和 token 消耗过高导致超时

最后他们采用的是一个 `xhigh-high-xhigh` 的“reasoning sandwich”启发式：规划阶段高、执行阶段相对低、验证阶段再拉高。这个做法说明，Harness Engineering 不只是决定“是否推理”，还要决定“在哪一步多花推理预算最划算”。

## 可以提炼出的几个工程结论

### 1. Harness 是 Agent 的实际工作环境

文章反复说明，模型本身并不是完整的 Agent。真正交付结果的是“模型 + prompt + 工具 + middleware + 执行流”这一整套系统。很多失败并不只是模型能力不够，而是 harness 没有把模型放进一个适合成功的环境里。

### 2. 验证能力比单次生成能力更重要

对编码 Agent 来说，最重要的不是“一次写对”，而是“能不能自己发现错、修回来”。测试、验证、回看任务规范，这些步骤本身就是 Agent 自主执行能力的一部分。没有验证闭环，再强的模型也容易停在第一个“看起来差不多”的答案上。

### 3. 环境信息应该由系统准备，而不是全交给模型自己摸索

目录结构、可用工具、测试方式、时间限制，这些都属于系统已知信息。把这些内容整理后注入给 Agent，能显著降低无意义搜索和环境误判。换句话说，Harness Engineering 的一个核心职责，就是“替 Agent 做好上下文准备”。

### 4. 中间件是很有价值的控制层

文章中的几个关键改进几乎都不是改模型，而是改 middleware：

- 退出前强制检查验证
- 启动时注入本地环境信息
- 检测重复编辑并提醒换思路

这说明 middleware 很适合作为工程上的“行为矫正层”。它不需要理解全部任务，但能在关键节点把已知正确做法再推一把。

### 5. 用 trace（执行轨迹）做闭环，才能持续改进 Agent

如果没有 trace（执行轨迹），很多失败看起来只像“模型不稳定”。但有了 trace，就能把失败拆成更具体的问题：

- 是规划错了
- 是工具没选对
- 是没验证
- 是时间花错阶段
- 还是掉进了循环

也只有这样，改进 harness 才会从“拍脑袋调 prompt”变成“针对失败模式做系统修复”。

## 我自己的理解

如果把这篇文章压成一句话，可以概括为：一个模型能不能真正变成一个好的 Agent 系统，关键往往不只是模型能力本身，而在于 `Harness Engineering` 是否足够稳定。

从工程角度看，这里的重点主要有三层。

第一层是**闭环机制**。一个好的 Agent 不能只会生成方案，还必须被放进“规划 - 执行 - 验证 - 修复”的闭环里。只有当系统明确要求它检查结果、运行验证、发现错误并继续修正时，模型能力才会更稳定地转化成任务完成能力。

第二层是**运行轨迹监控**。系统不能只看最终结果，还要持续记录和分析整个执行过程，也就是 trace（执行轨迹）。只有看到 Agent 每一步是怎么规划、怎么调用工具、怎么验证和在哪里失败，后续的优化才有抓手。很多看起来像“模型不稳定”的问题，真正拆开后其实是具体的执行模式问题。

第三层是**异常处理机制**。如果在运行轨迹里已经能识别出一些典型坏模式，例如反复修改同一文件、长时间停留在同一路径、持续调用低价值工具却没有推进结果，那么系统就不能只是继续放任模型往下跑，而应该主动插入额外处理机制，比如提醒、打断、重新规划或切换策略。这类机制的作用，本质上是在模型不够稳定的现实下，用工程手段补上保护层。

所以，这篇文章给我的核心启发是：Harness Engineering 的重点，不只是给模型接上工具，而是通过闭环、监控和异常处理，把模型放进一个更容易持续做对事的运行系统里。
