需要说明的是，目前 Multi-Agent System 并不存在一套唯一、统一、被所有研究共同采用的分类标准。不同研究会根据关注重点，从 Agent 组成、组织结构、控制关系、协作方式、任务执行、目标关系、通信机制等不同角度进行分类。

例如：

- Stone 与 Veloso 对 Multi-Agent System 的早期综述中，讨论了 Homogeneous / Heterogeneous、Communicating / Non-communicating、Benevolence / Competitiveness 等问题；
- Horling 与 Lesser 从 Multi-Agent Organization 的角度，总结了 Hierarchy、Holarchy、Coalition、Team、Federation、Market、Matrix Organization 等多种组织范式；
- 近年来针对 LLM Multi-Agent 的研究，则更多关注 Agent 角色、协作关系、控制结构、任务编排、通信与协调机制等问题；
- 《Multi-Agent Collaboration Mechanisms: A Survey of LLMs》从参与者、协作类型、结构、策略和协调协议等多个角度分析 LLM Multi-Agent；
- 针对 LLM Multi-Agent Orchestration 的研究，也进一步讨论了 Centralized、Decentralized、Hierarchical 等协调结构，以及任务路由、动态控制和 Handoff 等机制。

因此，下面这 5 个维度并不是一套严格、唯一的“Multi-Agent 标准分类法”，而是结合传统 Multi-Agent System 研究、现代 LLM Multi-Agent 研究以及当前 Agent 工程实践后，对一些比较核心、也比较常见的观察维度所做的个人总结。

本文主要从以下 5 个维度理解 Multi-Agent：

| 分类维度 | 核心问题 | 常见类型 |
| --- | --- | --- |
| **① 控制关系维度** | 谁来指挥谁？ | 集中式、去中心化、层级式、混合式 |
| **② 角色 / 能力维度** | Agent 之间能力是否一样？ | 同质智能体、异质智能体 |
| **③ 任务流转维度** | 任务如何在 Agent 之间移动？ | 串行、并行、分支、动态交接、混合 |
| **④ 协作关系维度** | Agent 之间是什么关系？ | 协作、竞争、协作-竞争混合 |
| **⑤ 通信关系维度** | Agent 之间怎么交换信息？ | 直接通信、共享状态/黑板、广播、间接通信 |

其中，我认为前 3 个维度尤其重要，因为它们能够比较直接地描述一个 Multi-Agent 系统：

- 谁控制谁；
- 不同 Agent 分别具有什么能力；
- 任务如何在 Agent 之间推进。

## 一、控制关系

Multi-Agent 中的控制和组织关系一直是传统 MAS 研究的重要问题。

Horling 与 Lesser 在 Multi-Agent Organizational Paradigms 的研究中讨论了 Hierarchy、Holarchy、Coalition、Team、Federation、Market、Matrix Organization 等组织结构。

进入 LLM Multi-Agent 阶段之后，Centralized、Decentralized、Hierarchical 等结构又被广泛用于描述多个 Agent 之间的控制和协调关系。

因此，为了理解现代 LLM Multi-Agent 中比较常见的控制结构，这里归纳为：

```text
控制关系
├── 集中式 Centralized
├── 去中心化 Decentralized
└── 层级式 Hierarchical
```

需要注意，这三种结构并不一定严格互斥。

例如，一个 Hierarchical 系统同时也可能具有较强的 Centralized 特征。因此，这里更适合把它们理解为几种常见的控制 / 组织形态，而不是严格互斥的数学分类。

### 1. 集中式 Centralized

核心特征：

存在一个中心 Agent，主要决策权集中在它手里。

结构例如：

```text
             Manager
          /     |      \
         A      B       C
```

执行过程可能是：

```text
用户任务
   ↓
Manager
   ├── 分配子任务给 A
   ├── 分配子任务给 B
   └── 分配子任务给 C
          ↓
       汇总结果
          ↓
       Manager 决策
```

例如，一个“软件开发多智能体系统”：

```text
Manager Agent
├── Research Agent：查资料
├── Coding Agent：写代码
└── Test Agent：执行测试
```

用户说：

“帮我实现一个登录模块。”

Manager 决定：

1. 要不要查资料；
2. 谁写代码；
3. 谁负责测试；
4. 测试失败之后交给谁修改；
5. 什么时候结束任务。

也就是说，A/B/C 更多是执行者，Manager 是主要的决策者和调度者。

优点是：

- 系统结构清晰；
- 控制逻辑集中；
- 比较容易进行状态管理和流程约束；
- 更容易保证整体任务按照预期方式执行。

但缺点也比较明显。

例如：

```text
Manager 出问题
      ↓
整个系统都可能受影响
```

中心 Agent 可能同时带来两个问题：

**单点故障 Single Point of Failure**

如果中心 Agent 无法正常工作，整个系统的调度和决策都可能受到影响。

**性能瓶颈 Performance Bottleneck**

如果所有任务分配、通信和决策都必须经过 Manager，那么随着 Agent 数量和任务数量增加，Manager 的处理能力可能限制整个系统的吞吐量和扩展性。

### 2. 去中心化 Decentralized

核心特征：

没有唯一的中央控制者，决策权分散在多个 Agent 中。

例如：

```text
A ←→ B
↕     ↕
D ←→ C
```

或者：

```text
Research Agent
      ↕
Coding Agent ←→ Test Agent
      ↕
Database Agent
```

比如 Coding Agent 写代码时发现：

“这里需要数据库设计。”

在集中式结构中，它可能需要：

```text
Coder → Manager → Database Agent
```

而在去中心化结构中，它可能直接：

```text
Coder → Database Agent
```

Database Agent 完成任务后，也可以根据当前情况决定下一步把结果交给哪个 Agent。

因此任务路径可能变成：

```text
A → B → D → C
```

甚至：

```text
A → C → A → D
```

这个路径可能是在系统运行过程中逐渐形成的，而不是由某个中央 Agent 在任务开始之前完整规划出来。

举一个简单场景：

```text
Research Agent：发现需要代码验证
      ↓
Coding Agent：发现需要测试
      ↓
Test Agent：发现数据库异常
      ↓
Database Agent
```

每个 Agent 都拥有一定程度的：

- 判断权；
- 任务转交权；
- 协作对象选择权。

所以：

去中心化 ≠ 没有规则。

而是：

不存在一个唯一 Agent 掌握整个系统的全部控制权。

### 3. 层级式 Hierarchical

层级式最容易和集中式混淆。

它的核心特征不是“有 Manager”，而是：

存在多层控制关系。

例如：

```text
                    Main Manager
                   /            \
          Research Manager     Dev Manager
            /      \             /      \
          R1       R2          Coder    Tester
```

这是一个明显的层级结构。

Main Manager 不一定直接控制所有 Agent。

例如：

```text
用户
 ↓
Main Manager
 ↓
“研究一下这个方案”
 ↓
Research Manager
 ├── Agent R1：查论文
 ├── Agent R2：查开源项目
 └── Agent R3：做对比
```

Research Manager 自己负责内部任务拆分。

于是决策权是分层的：

```text
Main Manager
    │
    ├── 全局决策
    │
Research Manager
    │
    ├── 研究任务内部决策
    │
Research Agents
```

再比如开发部分：

```text
Main Manager
      ↓
Dev Manager
   ├── Backend Agent
   ├── Frontend Agent
   └── Test Agent
```

这里：

- Main Manager：决定整个项目怎么推进；
- Dev Manager：决定开发任务如何推进；
- Backend Agent：只负责自己的具体工作。

因此它实际上类似现实中的：

```text
CEO
 ↓
部门经理
 ↓
组长
 ↓
员工
```

### 4. 三种类型最大的区别

| 类型 | 控制权在哪里 | 是否有中心 Agent | 是否多层 | Agent 自主性 |
| --- | --- | --- | --- | --- |
| 集中式 | 集中在中心 Agent | 是 | 不一定 | 较低 |
| 去中心化 | 分散在多个 Agent | 否 | 通常否 | 高 |
| 层级式 | 按层级分配 | 是 | 是 | 中等 |

其中最需要区分的是：集中式 vs 层级式

#### 集中式 vs 层级式

集中式强调的是：

主要决策权集中在一个中心。

例如：

```text
Manager
├── A
├── B
├── C
├── D
└── E
```

Manager 直接控制所有 Agent。

层级式强调的是：

权力分层。

例如：

```text
        Manager
       /       \
   Manager A   Manager B
    /    \      /    \
   A1    A2    B1    B2
```

所以：

层级式系统通常具有一定程度的集中控制，但集中式系统不一定具有多层级结构。

## 二、角色 / 能力维度

Homogeneous / Heterogeneous 是传统 Multi-Agent System 中非常经典的一组分类。

Stone 与 Veloso 在早期关于 Multi-Agent System 的综述中，就系统讨论过：

- Homogeneous Multi-Agent Systems；
- Heterogeneous Multi-Agent Systems。

因此，这里从角色 / 能力组成角度，将 Multi-Agent 简单归纳为：

```text
角色 / 能力
├── 同质智能体 Homogeneous
└── 异质智能体 Heterogeneous
```

需要注意：

现代 LLM Agent 中的“同质 / 异质”不能只看底层使用的模型。

Agent 之间的差异可能来自：

- Model；
- Role；
- Prompt；
- Tool；
- Knowledge；
- Memory；
- Permission；
- Goal。

因此，这里的 Homogeneous / Heterogeneous 更适合描述：

多个 Agent 在系统中承担任务时，整体能力配置的相似程度。

### 1. 同质智能体

每个 Agent 的：

- 角色；
- 模型；
- 工具；
- Prompt；
- 能力配置；

整体上比较接近，没有明显的专业能力分工。

例如：

```text
Research Agent 1
Research Agent 2
Research Agent 3
```

三个 Agent 同时搜索不同资料。

常见用途是：

并行扩展、投票、多样性采样、提高吞吐量。

例如让三个能力类似的 Agent 分别回答同一个问题：

```text
             ┌→ Agent A
Task ────────┼→ Agent B
             └→ Agent C
                  ↓
                投票
```

这里并不要求三个 Agent 的所有配置参数完全相同。

核心是：

它们在系统中的功能定位比较接近，具有较高的可替代性。

### 2. 异质智能体

异质智能体是指不同 Agent 在角色、能力、工具、模型或者知识等方面存在明显差异。

例如：

```text
Planner
   ↓
Coder
   ↓
Reviewer
   ↓
Tester
```

例如：

- Planner：任务规划
- Coder：写代码
- Reviewer：代码审查
- Tester：测试

现在 LLM Multi-Agent 系统里，异质智能体其实更加常见。

## 三、任务流转

这个维度描述的是：

一个任务进入 Multi-Agent 系统之后，会沿着什么路径在不同 Agent 之间推进。

可以分成：

```text
任务流转
├── 串行
├── 并行
├── 分支
├── 动态交接
└── 混合
```

并不是传统 Multi-Agent 领域长期存在的一套统一标准分类。

这里更多是结合现代 LLM Multi-Agent 中的：

- Workflow；
- Task Decomposition；
- Task Allocation；
- Control Flow；
- Agent Interaction；
- Dynamic Routing；
- Handoff；

等工程实践所做的个人归纳。

### 1. 串行

```text
A → B → C → D
```

上一个 Agent 的输出成为下一个 Agent 的输入。

例如：

```text
需求分析
  ↓
方案设计
  ↓
代码生成
  ↓
代码审查
```

这种模式的特点是：

任务按照相对明确的顺序逐步推进。

适合：

- 前后依赖明显的任务；
- 流程比较固定的任务；
- 一个步骤必须依赖上一步结果的任务。

### 2. 并行

```text
        ┌→ Agent A ─┐
Task ───┼→ Agent B ─┼→ 汇总
        └→ Agent C ─┘
```

多个 Agent 同时处理任务。

例如让三个 Agent 分别：

- 查技术资料
- 查论文
- 查开源项目

最后统一汇总。

并行方式的主要优势是：

- 提高执行速度；
- 提高吞吐量；
- 同时获取多种信息；
- 减少互相独立任务之间不必要的等待。

### 3. 分支

分支的重点不是“同时执行”，而是：

根据条件选择不同路径。

例如：

```text
            ┌→ Coder
Planner ────┤
            ├→ Researcher
            └→ Data Analyst
```

如果任务是：

```text
写代码 → Coder
查资料 → Researcher
分析数据 → Data Analyst
```

所以：

并行强调同时执行，分支强调路径选择。

### 4. 动态交接

动态交接则更像：

当前 Agent 在运行过程中自己决定“这个事情应该交给谁”。

例如：

```text
Agent A
   ↓
发现需要数据库知识
   ↓
handoff → Database Agent
   ↓
发现需要写代码
   ↓
handoff → Coding Agent
```

任务路径事先不一定固定：

```text
A → ?
```

运行之后才逐渐形成：

```text
A → C → B → E
```

这个决策可能由：

- 当前 Agent；
- Router；
- Orchestrator；
- Manager；
- 动态路由规则；

等机制完成。

这在现代 Agent Harness 中非常重要。

## 四、目标/利益关系

合作与竞争是传统 Multi-Agent System、Multi-Agent Learning 以及 Game Theory 中长期存在的重要研究问题。

近年来针对 LLM Multi-Agent Collaboration 的研究，也继续讨论：

- Cooperation；
- Competition；
- Coopetition。

因此，这里将目标 / 利益关系归纳为：

```text
目标 / 利益关系
├── 合作型 Cooperative
├── 竞争型 Competitive
└── 竞合型 Coopetition
```

该维度描述的是：

多个 Agent 在系统中的目标和利益是否一致，以及彼此之间是否存在冲突。

### 1. 合作型 Cooperative

合作型是指多个 Agent 的目标基本一致，各 Agent 通过分工共同完成一个最终任务。

例如：

```text
           用户任务
              ↓
           Planner
          /       \
      Coder      Researcher
          \       /
           Reviewer
              ↓
           最终结果
```

其中：

- Planner：负责分析和拆解任务；
- Researcher：负责查找和整理信息；
- Coder：负责具体实现；
- Reviewer：负责检查结果。

虽然不同 Agent 的职责不同，但它们服务于同一个最终目标，因此属于合作型关系。

常见应用场景包括：

- 软件开发；
- 复杂研究；
- 文档处理；
- 自动化工作流；
- 多步骤任务执行。

合作型是当前以完成用户任务为主要目的的 LLM Multi-Agent 系统中最常见的一种关系。

### 2. 竞争型 Competitive

竞争型是指多个 Agent 的目标、收益或利益之间存在冲突，各 Agent 会倾向于最大化自身目标或收益。

例如，在有限资源环境中：

```text
              有限资源
             /       \
        Agent A     Agent B
           ↑           ↑
      最大化收益    最大化收益
```

Agent A 获得更多资源，可能意味着 Agent B 获得的资源减少，因此两者之间存在竞争关系。

另一个典型场景是市场竞争：

```text
企业 Agent A ─┐
企业 Agent B ─┼──→ 竞争客户、资源、市场份额
企业 Agent C ─┘
```

不同 Agent 都希望获得更多收益，因此彼此之间存在利益冲突。

常见应用场景包括：

- 博弈环境；
- 市场模拟；
- 拍卖系统；
- 资源竞争；
- 多方谈判；
- 策略决策。

需要特别注意：

竞争型的核心并不是“Agent 之间互相反驳”

例如让两个 Agent：

```text
Agent A：提出方案
Agent B：反驳方案
```

如果它们最终仍然服务于同一个任务目标，这种 Debate 机制本质上仍然可能属于 Cooperative。

真正的 Competitive 更强调：

不同 Agent 的目标函数、收益或者利益之间存在冲突。

### 3. 竞合型 Coopetition

竞合型是 Cooperation（合作）与 Competition（竞争）的结合。

其核心特点是：

Agent 在部分目标上利益一致，需要合作；但在另外一些目标或收益上又存在竞争。

例如多个企业 Agent：

```text
                 市场整体运行
                      ↑
          ┌───────────┼───────────┐
          │           │           │
      Agent A      Agent B      Agent C
```

这些 Agent 可能需要共同遵守市场规则、维护行业生态，因此存在合作关系。

但同时：

```text
Agent A ↔ Agent B ↔ Agent C
      竞争客户、资源和收益
```

它们又会争夺：

- 客户；
- 市场份额；
- 资源；
- 利润。

因此，同一组 Agent 之间可以同时存在合作与竞争。

常见应用场景包括：

- 市场和经济模拟；
- 多组织协同；
- 供应链系统；
- 联盟系统；
- 多方资源协调；
- 复杂博弈环境。

### 4. 三种关系的区别

| 类型 | Agent 目标关系 | 核心特点 | 典型场景 |
| --- | --- | --- | --- |
| **合作型 Cooperative** | 目标高度一致 | 共同完成一个目标 | 软件开发、研究分析、复杂工作流 |
| **竞争型 Competitive** | 目标或收益存在冲突 | 各自追求自身收益 | 博弈、市场竞争、拍卖、资源竞争 |
| **竞合型 Coopetition** | 部分一致、部分冲突 | 合作与竞争同时存在 | 市场生态、供应链、多组织协同 |

可以简单理解为：

合作型：

我们的目标基本一致，一起完成任务。

竞争型：

我们的利益存在冲突，你获得更多可能意味着我获得更少。

竞合型：

我们在部分目标上合作，同时又在其他利益上竞争。

## 五、通信机制

该维度描述的是：

多个 Agent 之间的信息以什么关系进行传递和共享。

Agent Communication 是传统 Multi-Agent System 中一个非常重要的研究方向。

早期 Multi-Agent 研究中就已经讨论过：

- Point-to-Point；
- Broadcast；
- Blackboard。

其中 Blackboard Architecture 是一种非常经典的间接通信方式：

多个 Agent 不一定直接互相发送消息，而是通过一个公共信息空间交换信息。

现代 LLM Multi-Agent 中，这些思想又进一步发展为：

- Agent-to-Agent Message；
- Group Message；
- Shared Memory；
- Shared State；
- Shared Context；
- Shared Workspace；

等机制。

因此，为了便于理解现代 Agent 系统，这里将比较常见的通信形式归纳为：

```text
通信关系
├── 点对点通信 Point-to-Point
├── 广播通信 Broadcast
└── 共享空间通信 Shared-Space
```

需要注意：

这三种同样不是所有 Multi-Agent Communication 的全部形式。实际系统中还可能存在：Publish / Subscribe、Message Bus、Event Bus等机制。

### 1. 点对点通信 Point-to-Point

点对点通信是指一个 Agent 将消息直接发送给另一个明确的 Agent。

```text
Agent A → Agent B
```

例如：

```text
Planner → Coder
Coder → Reviewer
Reviewer → Coder
```

这种通信关系中，发送者通常明确知道消息要交给哪个 Agent。

常见应用场景：

- Agent 之间的任务交接；
- Planner 向指定 Agent 分配任务；
- Agent 请求其他专业 Agent 提供能力；
- Reviewer 将修改意见反馈给 Coder；
- 多 Agent 工作流中的结果传递。

特点：

通信目标明确、结构清晰，适合 Agent 职责和任务边界比较明确的系统。

### 2. 广播通信 Broadcast

广播通信是指一个 Agent 将信息同时发送给多个 Agent，或者系统中的所有相关 Agent。

```text
             → Agent B
Agent A ────→ Agent C
             → Agent D
```

例如系统发现任务要求发生变化：

```text
Manager
  │
  ├──→ Planner
  ├──→ Coder
  ├──→ Reviewer
  └──→ Tester
```

所有相关 Agent 都能够收到这条信息。

常见应用场景：

- 全局任务状态更新；
- 环境发生变化；
- 用户需求发生变化；
- 系统级通知；
- 多个 Agent 需要同步相同信息。

特点：

信息传播范围较大，适合需要快速同步全局信息的场景。

但随着 Agent 数量增加，广播过多也可能带来：

- 通信开销增加；
- 信息冗余；
- 无关信息增加；
- Agent 上下文压力增加。

### 3. 共享空间通信 Shared-Space

共享空间通信是指多个 Agent 不一定直接互相发送消息，而是通过一个公共的信息空间读取和写入数据，从而实现间接通信。

```text
Agent A ─┐
Agent B ─┼──↔ Shared Space
Agent C ─┘
```

共享空间可以表现为：

```text
Shared Memory
Shared State
Shared Context
Shared Workspace
Blackboard
```

例如：

```text
              Shared Context
             /      |       \
        Planner   Coder   Reviewer
```

Planner 将任务信息写入 Shared Context：

任务 A 已完成拆解

Coder 从 Shared Context 中读取任务并执行，然后写入：

模块 A 已完成

Reviewer 再读取这些状态进行检查。

整个过程中不一定存在：

```text
Planner → Coder
```

这样的直接消息，而是：

```text
Planner → Shared Space ← Coder
```

常见应用场景：

- 多 Agent 共同维护任务状态；
- Blackboard 架构；
- 多 Agent 共享上下文；
- 动态 Agent 系统；
- Agent Harness 中的 Shared Context / Workspace。

特点：

Agent 之间耦合较低，不需要始终知道应该把信息发送给哪个具体 Agent，更适合动态协作和复杂任务状态管理。

### 4. 三种通信关系的区别

| 类型 | 信息传递方式 | 接收对象 | 典型场景 |
| --- | --- | --- | --- |
| **点对点通信** | Agent 直接发送消息 | 一个明确 Agent | 任务交接、能力调用、结果反馈 |
| **广播通信** | Agent 向多个 Agent 传播消息 | 多个或全部 Agent | 全局通知、状态同步、环境变化 |
| **共享空间通信** | 通过公共空间读写信息 | 不指定具体接收者 | Shared Context、Blackboard、复杂协作 |

可以简单理解为：

点对点：

我把消息直接发给你。

广播：

我把消息告诉大家。

共享空间：

我把信息放到公共区域，谁需要谁来读取。

## 多维度理解

理解 Multi-Agent 分类时，非常重要的一点是：

这些维度不是互相排斥的“唯一类型标签”，而是从不同角度观察同一个 Multi-Agent 系统。

例如，一个系统完全可以同时是：

```text
控制关系：层级式
角色/能力维度：异质
任务流转：并行 + 动态交接
目标/利益关系：协作型
通信机制：共享 Context + Message
```

例如：

```text
                     Manager
                 /      |      \
          Researcher   Coder   Analyst
              │          │       │
              └──── Shared Context ────┘
                         │
                      Reviewer
```

因此，一个系统并不是简单地：

“属于某一种 Multi-Agent。”

更准确的说法应该是：

这个 Multi-Agent 系统在不同维度上分别采用了什么结构和机制。

而且，即使在同一个维度内部，也不一定只能选择一种形式。

## 关于本文分类方式的说明

最后需要再次说明：

本文总结的 5 个维度并不是一套统一、权威或者穷尽性的 Multi-Agent 分类标准，而是我在学习传统 Multi-Agent System、LLM Multi-Agent、Agent Harness 和 Agent Orchestration 相关资料之后，为了方便理解和分析现代 Multi-Agent 系统所做的一种个人总结。

其中：

- “同质 / 异质”等分类在传统 MAS 研究中具有比较明确的文献基础；
- “合作 / 竞争”等关系同样长期存在于 MAS、Multi-Agent Learning 和 Game Theory 研究中；
- “Hierarchy”等结构属于传统 Multi-Agent Organization 的重要研究内容；
- “Centralized / Decentralized / Hierarchical”等结构在现代 LLM Multi-Agent Orchestration 中仍然被大量使用；
- “Point-to-Point / Broadcast / Blackboard”等通信形式能够追溯到传统 Multi-Agent Communication 研究；
- “串行 / 并行 / 分支 / 动态交接 / 混合”则更多是结合现代 LLM Agent Workflow、Dynamic Routing 和 Handoff 等实际机制进行的工程化归纳。

因此，这套分类更适合被理解为：

一个用于观察、理解、分析和设计 Multi-Agent 系统的框架，而不是一套边界绝对明确的分类法。

与此同时，这些分类本身也不是绝对的。

随着系统复杂度增加，一个实际 Multi-Agent 系统往往不会完全采用某一种模式，而是根据具体场景混合使用不同结构。

例如：

```text
简单、流程明确的任务
→ Centralized + Sequential

大量相互独立的搜索任务
→ Homogeneous + Parallel

复杂软件开发
→ Hierarchical + Heterogeneous + Shared Context

动态开放式任务
→ Decentralized / Hierarchical + Dynamic Handoff
```

甚至同一个系统在不同阶段也可能采用不同机制。

例如：

```text
规划阶段：
Centralized

执行阶段：
Parallel

异常处理阶段：
Dynamic Handoff

全局状态管理：
Shared Context
```

因此，分类的真正价值并不是：

给一个 Multi-Agent 系统强行贴上一个唯一标签。

而是帮助我们理解几个更重要的问题：

1. 系统中的控制权如何分配；
2. 不同 Agent 如何进行能力分工；
3. 任务如何在不同 Agent 之间推进；
4. Agent 之间为什么合作或者竞争；
5. 信息如何在 Agent 之间传递和共享。

对于 Agent Harness / LLM Multi-Agent 的学习，我个人认为最值得优先理解的是：

```text
控制关系
   ↓
角色 / 能力
   ↓
任务流转
   ↓
通信机制
```

因为这几个维度已经能够帮助我们描述相当一部分现代 LLM Multi-Agent 系统的基本运行形态。
